# Spec: Release-readiness gate for Field 1.0

The build that has been tested is not the build that would ship. Every manual and automated
check so far has run against the **debug** variant. The release variant turns on R8
(`isMinifyEnabled = true`, `isShrinkResources = true`), has an empty `proguard-rules.pro`, and
has **never been built** (`app/build/outputs/` contains only `apk/debug` and `apk/androidTest`,
and there is no `mapping/` directory). Most of what follows comes from that one gap.

## 0. Open questions (each answer changes scope)

1. **Should the demo roster ship to real coaches?** The prepackaged `alearning.db` contains 5
   athletes, 2 groups ("Varsity Football", …), 10 testing events and 200 results, and
   `SeedDataManager` step 3 seeds the same set on a CSV-path install. Every coach who installs
   1.0 opens the app to someone else's team.
   - **(a) Keep it** as an onboarding sample (status quo). The spec adds only a smoke check that
     it deletes cleanly.
   - **(b) Strip it from release**: drop the demo rows from `build_prepackaged_db.py` and gate
     step 3 behind a debug check. This is a small data change, but it touches the catalog stamp.
   - *This document assumes (a)* because it is the current behaviour. Say "(b)" and §5 gains
     one step.
2. **Distribution channel: Play Store, or a GitHub-release APK?** Play needs an AAB, Play App
   Signing (which introduces a *second* SHA-1 that Drive OAuth has to know), a privacy policy,
   the Data-safety form and the current target-API level. A sideloaded APK needs none of those.
   *Assumes Play Store*, matching `deployment_status` memory.

## 1. Objective & scope

## 3. Root cause / findings, ranked

### B1 — R8 will rename every field Gson serializes (blocker, verified mechanism)

`BackupRepositoryImpl` writes and reads the Drive backup with plain reflection:

```kotlin
val json = gson.toJson(payload)                       // :164
gson.fromJson(json, BackupPayload::class.java)        // :194
```

`BackupPayload` and its nested `Backup*` classes carry no `@SerializedName` and no `@Keep`
(grep finds none in `app/src/main`), and `proguard-rules.pro` contains only the template
comments. Gson 2.11's bundled rules keep `@SerializedName` fields and `TypeToken` signatures;
they do **not** keep the names of unannotated data-class fields. R8 therefore renames
`individuals`, `testResults`, `medicalAlert`, … to `a`, `b`, `c`.

What that produces:

| Scenario | Outcome |
|---|---|
| Back up and restore on the same release build | Probably works, because both sides use the same renamed names. *Inferred.* |
| Restore a backup written by a **debug** build, or by any pre-release build | Every key is unknown, so every list comes back null and the restore fails or comes back empty. |
| Restore a 1.0 backup on 1.1 | R8 reassigns short names whenever classes change, so the keys no longer line up. **A coach's backup silently stops being restorable after an app update.** |

The last row is the dangerous one: it would not show up in any test done before launch, and
the first coach to hit it is the one who has just lost their phone.

The same applies to `CustomPresetsStore.StoredPreset`, which is stored in SharedPreferences, so
custom stopwatch presets would vanish on update, and to the Drive API model classes used through
`GsonFactory` in `DriveBackupHelper`. Those rely on `@com.google.api.client.util.Key` field
reflection. Whether the google-http-client jar ships consumer rules for them is unverified; the
release build in §7 settles it.

### B2 — Sign-up crashes on Android 7.0/7.1 (blocker, verified mechanism)

`minSdk = 24`, but `PasswordHasher` uses `SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256")`,
which Android's provider only supports from **API 26**. On API 24–25 it throws
`NoSuchAlgorithmException`. In `AuthRepositoryImpl.signUp`, `hasher.hash(password)` (line 50) is
called **outside** the `try` at line 63, so the exception escapes the repository. Whether a use
case or the ViewModel catches it further up was not traced, so a crash rather than an error
message is *inferred*. Either way, an Android 7 coach cannot create an account, and nothing in
the app works without one.

### B3 — No release signing, and Drive OAuth isn't registered for the shipping key (blocker, manual)

- No `signingConfigs` block exists; `assembleRelease` produces an unsigned APK.
- `deployment_status` memory records that the verified OAuth Android client is still registered
  to the old `com.example.alearning` package. Drive authorization (`Identity.getAuthorizationClient`)
  checks package name + SHA-1. With Play App Signing the SHA-1 that matters on users' phones is
  the **app-signing key** Play generates, which is not your upload key. You need OAuth clients
  for `com.vamshi.field` with the upload-key SHA-1 (for internal testing of your own builds)
  **and** the Play app-signing SHA-1 (shown in Play Console → Setup → App signing). If either is
  missing, backup fails with `DEVELOPER_ERROR` only in production.

### B4 — Target API level is likely below Play's floor (blocker if Play; verify)

`targetSdk = 35`. Play's rule is that new apps target within a year of the latest major Android
release; that floor is expected to have moved to API 36 on 2026-08-31. **Confirm in Play
Console before acting** — this is from policy memory, not a file. Going to 36 needs
`compileSdk = 36` and brings Android 16 behaviour changes into scope, chiefly that the edge-to-edge
opt-out stops working and predictive back becomes the default. The adaptive screens need a visual
pass afterwards. A system image for API 36 is already installed under `D:\Android\Sdk`.

### B5 — The release would be cut from an uncommitted tree (blocker, process)

20 modified files plus untracked `app/schemas/.../17.json`, `CatalogMetadataEntity.kt`, the
`baselineprofile/` module and new tests. `17.json` matters most: without it in git,
`MigrationTest` on a fresh clone has no schema for 17, and a future maintainer cannot write
`MIGRATION_17_18`. Tag the release commit so the R8 `mapping.txt` can be matched to it.

### S1 — Android Auto Backup is on with template rules (decide before Data-safety form)

`allowBackup="true"` with both rule files still the Android Studio placeholders means Google's
device backup copies the whole Room DB (athletes' DOB, medical alerts, PBKDF2 hashes) and
SharedPreferences (session, seed flags) to the user's Google account, alongside Field's own
Drive backup. It works, but it is undeclared. Recommendation: set `allowBackup="false"`.
The explicit Drive backup is the supported path, and two silent restore paths are harder for an
unknown future maintainer to reason about. The alternative is to write real include/exclude
rules.

### S2 — Store compliance items (manual, Play only)

Privacy policy URL, Data-safety form, target audience and content questionnaire, and the
$25 developer account. The app stores children's names, ages and medical notes **on device
only**, and Drive backups go to the coach's own `appDataFolder`. That is "no data collected by
the developer", but the form still asks about it, and an athlete roster of 5–12-year-olds puts
the Families policy questions in play.

### S3 — Release startup is unmeasured (should-check)

The 6.2s first launch and ~4.5s cold start were measured on **debug**. The `baselineprofile`
module is wired up, but `src/main/generated/baselineProfiles` does not exist yet, so no profile
ships. Measure release cold start in §7 before deciding whether that spec needs to block.

## 5. Fix, in order

0. **Clear the 2 lint errors** from §7.1 (`@RequiresApi(Q)` in `CsvExporter`, indentation in
   `SeedDataManager`).
1. **Commit the current tree** (B5) after §7.1 is green, as its own commit, so later changes diff
   against a known base.
2. **`minSdk 24 → 26`** (B2). Lower risk than adding a fallback KDF: a fallback would need a
   hash-format version byte in `UserEntity` and a migration, while API 24–25 is a small share of
   active devices. Note that hashes created on one device restore through backup on any other
   device ≥ 26, so no data compatibility issue arises.
3. **Keep rules** (B1), in `proguard-rules.pro`:
   ```proguard
   # Backup JSON is a persisted contract: field names ARE the format.
   -keep class com.vamshi.field.domain.model.backup.** { <fields>; <init>(...); }
   -keep class com.vamshi.field.data.storage.CustomPresetsStore$StoredPreset { <fields>; }
   # google-http-client reflects over @Key fields of the Drive model classes.
   -keepclassmembers class * { @com.google.api.client.util.Key <fields>; }
   -keepattributes Signature,*Annotation*,EnclosingMethod,InnerClasses
   # No debug chatter in release.
   -assumenosideeffects class android.util.Log { public static int d(...); public static int v(...); }
   ```
   Confirm the `StoredPreset` binary name (nested vs top-level) against the source before
   pasting. Why keep rules and not `@SerializedName` on every field? There are ~10 DTOs with
   ~100 fields, and one missed annotation re-opens the bug. A package-level keep can't miss a field.
4. **Signing** (B3): generate an upload keystore *outside the repo*, and back it up somewhere
   that isn't this laptop. Losing it means asking Play support for an upload-key reset. Add a
   `signingConfigs { create("release") { … } }` block that reads `rootProject.file("keystore.properties")`
   and skips signing when the file is absent, so CI and contributors can still build.
5. **Target API** (B4), only if Play Console confirms 36: bump `compileSdk`/`targetSdk`, build,
   then run the visual pass in §7.4 on API 36.
6. **Manifest** (S1).
7. **Version:** `versionCode 1`, `versionName "1.0.0"`. Leave `versionCode` at 1 for the first upload.
8. **Google Cloud Console** (manual, B3): Android OAuth client for `com.vamshi.field` + upload
   SHA-1 now; a second one with the Play app-signing SHA-1 after the first AAB upload.
9. Docs and hygiene from §4.

## 6. Constraints for this change

- **Backup JSON is now a frozen public format.** After 1.0 ships, renaming any `Backup*` field
  breaks every coach's existing backup. `BackupJsonContractTest` exists to make that a red build
  instead of a support email. New fields stay nullable `= null` (see the `BackupPayload` KDoc).
- **Do not regenerate or touch the catalog stamp** for any of this. None of it changes the CSVs,
  so `CATALOG_VERSION` stays `v31` and the DB stays at 17.
- **The keystore never enters git.** Recovering from a leaked key is a Play support ticket and a
  new upload key. Recovering from a lost key without Play App Signing means a new app listing.
- **Medical alerts:** the smoke path must confirm `medicalAlert`/`isRestricted` survive the
  release backup → reinstall → restore round-trip. This is the field R8 is most likely to break
  silently, and the one that matters most.
