# Spec: Remove dead code, staged by risk

## 0. Open question (answer changes scope)

Two of the findings below are not cruft — they are features that were built, wired through
every layer, and then never connected to a screen. Deleting them is one reasonable call;
finishing the wiring is another. This spec **deletes** both, on the grounds that unreachable
code that looks live is worse than no code. Say so if either should instead be finished, and
that stage becomes its own spec:

- **Pending test entries (Stage 3).** `pending_test_entries` exists as a table, entity, DAO,
  mapper, repository and five use cases. `StopwatchViewModel` keeps in-flight scores in an
  in-memory `Map` instead, so **staged scores do not survive process death today**, despite
  the schema being there for exactly that. `DEVELOPMENT_CONTEXT.md` and the project notes both
  describe this as working.
- **The four `OnDismissError` actions (Stage 1).** They are handled in the ViewModel and
  dispatched by nobody, which means the error banner on Athlete Test Detail, Group Overview,
  Session Report and Reports Hub **cannot currently be dismissed by the coach**. Deleting the
  action makes the code honest; wiring it fixes the screen. This spec deletes, and flags the
  four screens for a follow-up.

Everything else below is unambiguous dead code.

## 1. Objective & scope

- **As the next maintainer**, I want the tree to contain only code that runs, so that reading
  a use case tells me something true about the app.
- **In scope:** deleting unreferenced files, declarations, unreachable action branches, unused
  resources and unused Gradle dependencies; and the schema change that removes the dead table
  and columns.
- **Out of scope:** the ~14 ViewModels that inject repositories directly instead of use cases,
  the 60/30-vs-80/40 percentile drift in `QuickTestScreen` / `TestingGridComponents`, and
  rewriting any screen. None of that is dead code.

## 4. Contracts

The only new declaration in the whole change:

```kotlin
// data/AppDatabase.kt, inside the companion object, alongside MIGRATION_14_15

/**
 * Migration 15 -> 16: drops `pending_test_entries` and the three unused
 * security-question columns on `users`.
 *
 * `pending_test_entries` was never written to — staged stopwatch scores live in
 * StopwatchUiState — so dropping it cannot lose coach data. The `users` columns
 * were only ever populated by the removed ResetPassword flow; OnboardingUseCase
 * has always passed null for both.
 */
val MIGRATION_15_16 = object : androidx.room3.migration.Migration(15, 16) {
    override suspend fun migrate(connection: SQLiteConnection) {
        connection.execSQL("DROP INDEX IF EXISTS `index_pending_test_entries_eventId`")
        connection.execSQL("DROP TABLE IF EXISTS `pending_test_entries`")

        // Table rebuild rather than ALTER TABLE ... DROP COLUMN: the rebuild is the
        // portable form across every SQLite the app can be running on (bundled and
        // framework), and it lets the recreated table match the exported schema exactly.
        connection.execSQL(
            """
            CREATE TABLE IF NOT EXISTS `users_new` (
                `id` TEXT NOT NULL,
                `firstName` TEXT NOT NULL,
                `lastName` TEXT NOT NULL,
                `username` TEXT NOT NULL,
                `email` TEXT,
                `passwordHash` BLOB NOT NULL,
                `passwordSalt` BLOB NOT NULL,
                `createdAt` INTEGER NOT NULL,
                PRIMARY KEY(`id`)
            )
            """.trimIndent()
        )
        connection.execSQL(
            """
            INSERT INTO `users_new` (id, firstName, lastName, username, email, passwordHash, passwordSalt, createdAt)
            SELECT id, firstName, lastName, username, email, passwordHash, passwordSalt, createdAt FROM `users`
            """.trimIndent()
        )
        connection.execSQL("DROP TABLE `users`")
        connection.execSQL("ALTER TABLE `users_new` RENAME TO `users`")
        connection.execSQL("CREATE UNIQUE INDEX IF NOT EXISTS `index_users_username` ON `users` (`username`)")
    }
}
```

`AuthRepository.register` loses its last two parameters; the call site in
`OnboardingUseCase.kt:57-59` loses the two `= null` arguments. Nothing else changes signature.

### 5.5 Stages 3 and 4 — the schema change

Order matters; each step compiles on the last.

1. **Kotlin first.** Delete the eleven pending-entry files, the two DI members, the entity from
   `@Database(entities = [...])` and `abstract fun pendingTestEntryDao()`. Apply the Stage 4
   edits to `AuthRepository`, its impl, `FakeAuthRepository`, `UserEntity`, `AuthResult`,
   `BackupPayload`, `BackupRepositoryImpl` and `OnboardingUseCase`.
2. **Bump `version = 15` to `16`** in `data/AppDatabase.kt` and add `MIGRATION_15_16` from §4.
3. **Register it** in `di/DatabaseModule.kt`'s `.addMigrations(...)` chain, after
   `MIGRATION_14_15`. An unregistered migration is a runtime `IllegalStateException`, not a
   compile error.
4. **Build once** so KSP emits `app/schemas/com.vamshi.field.data.AppDatabase/16.json`, and
   commit that file.
5. **Rebuild the prepackaged asset.** In `tools/build_prepackaged_db.py`: delete the two
   `pending_test_entries` statements (63-64), rewrite the `users` `CREATE TABLE` (61) without
   the three columns, change `PRAGMA user_version = 15` to `16` (240), and — the step that is
   easy to miss — **copy the new `identityHash` out of `16.json` into the hardcoded
   `room_master_table` insert at line 69.** A stale hash makes every fresh install crash on
   first open with an identity-mismatch `IllegalStateException`. Then run
   `gradlew generatePrepackagedDb`, or let `assembleDebug` do it via the `dependsOn` at
   `app/build.gradle.kts:203`.
6. **Extend `MigrationTest.kt`** per §7.

On `BackupPayload`: removing a field is the safe direction. Gson ignores JSON keys with no
matching field, so a backup written by an older build still restores. The reverse — adding a
field — is what requires `= null` and a `?:` at the restore site, and nothing is being added here.

## 6. Constraints for this change

- **`MIGRATION_15_16` must not touch coach data.** It drops a table that was never written to
  and three columns that `OnboardingUseCase` has always passed `null` for. Nothing in
  `testing_events`, `test_results`, `event_test_cross_ref`, `individuals`, `groups` or
  `group_members` is in scope, and the `users` rebuild copies every surviving row.
- **The prepackaged asset and the Room schema must agree exactly**, identity hash included.
  They are two hand-maintained copies of one schema. This is the failure mode that bricks a
  *fresh install* rather than an upgrade, so it will not reproduce on a device that already has
  the database — test it on a clean one.
- **The seed key does not need bumping.** No catalog table (`test_categories`, `fitness_tests`,
  `norm_references`, the recommendation tables) changes, so leave `data_seeded_version_v30` alone.
- **`WRITE_EXTERNAL_STORAGE` is NOT dead.** It was listed as removable in the original
  survey; that was wrong. `CsvExporter.saveToDownloadsLegacy` checks it explicitly before
  writing to the public Downloads directory on API < 29, and minSdk is 24, so removing it
  makes "save CSV to Downloads" fail silently on API 24-28. Only the *share* path goes
  through `FileProvider`.
- **`ui/theme/Color.kt` is generated.** Editing it directly is reverted by the next build; the
  change belongs in `design.md` §12.
- **`Converters`, the `di/` provider functions, `FieldApplication`, `MainActivity` and the two
  `@Preview`s have no Kotlin callers by design** — Room codegen, Hilt, the manifest and the IDE
  call them. Any future automated dead-code sweep will flag them again; it is wrong both times.

## 7. Verification

observable changes. The equivalent guard is the new migration test, which fails if

    `username` still exists, and `pending_test_entries` is gone.
  - `migrate15To16_onEmptyDatabase_validatesSchema` — the schema-only case.
- **Instrumented, existing:** `StandardsDaoSourceScopingTest` and `ResponsiveGridTest` must still pass.
- **Unit:** the whole `app/src/test` suite, in particular `BackupRepositoryImplTest` (Stage 4
  changes the payload) and the `domain/usecase/auth` tests (`FakeAuthRepository` loses three
  overrides). `SeedNormsConsistencyTest` should be untouched.
- **Build:** `gradlew assembleDebug`, then `gradlew test`, then `gradlew lint` to confirm the
  import cleanup left no warning behind.
- **Manual, after Stages 3–4, on a device that already holds data:**
  1. Install the *previous* build. Register a coach, create a group and an athlete, run a
     stopwatch session, save a score.
  2. Install this build over it. The app must open to Unlock, not Onboarding — that is the
     `users` rebuild working.
  3. Roster, the session report and the athlete dashboard all show the pre-upgrade data.
  4. Settings → back up to Drive, then restore. The coach account and all data return.
  5. Uninstall completely, install fresh. The app must open without an identity-hash crash and
     the seeded test catalog must be present — that is the prepackaged-asset step.

**Why this wasn't caught:** nothing fails when an action variant is handled but never
dispatched — Kotlin checks that a `when` is exhaustive, not that every branch is reachable —
and there is no test anywhere that asserts a declaration is reachable at all. The four
undismissable error banners are the visible cost of that gap, and they went unnoticed because
no UI test exercises an error state on those four screens.
